# results_NoTC 分析レポート

## 結論

今回の16試行では、TCPメトリクスをブラウザへ渡し、選択条件に応じてABR
Guardrailを動作させるAPI経路自体は確認できた。一方、NoTC環境で現在のRTTx判定を
有効にすると、ほぼすべてのTCPサンプルが輻輳扱いになり、品質の頻繁な上下動、
平均ビットレートの低下、再生停止の増加につながった。

LossとCWNDは全試行で判定条件が一度も成立せず、品質変更には寄与していない。
したがって、このデータから「RTT・CWND・Lossのどれが最も有効か」を比較することは
できず、分かったのは主に「現在のRTT正規化とGuardrail制御には誤検出・発振を
抑える修正が必要」ということである。

## 分析対象と方法

- 対象: 16ログ（Throughput/BOLA × TCP信号8組合せ）
- TCP輻輳制御: 全21,995サンプルがCUBIC
- 各条件1試行
- 動画再生位置: 約596.3～596.5秒まで全条件で完走
- 平均品質・平均ビットレート: 再生中の1秒間隔HEARTBEATから算出
- Playback excess: 総所要時間 - 最終再生位置 - 起動時間
- Packet loss: TCP再送率から求めた推定値

Playback excessは、記録されたstallに加え、stallイベントで捕捉されなかった停止や
スケジューラ待ちも含む。各条件1試行なので、以下は統計的有意差ではなく観測結果である。

## TCPメトリクスから分かること

### 1. RTT判定はNoTC環境でもほぼ常時成立している

- 平均RTT: 0.081～0.444 ms
- RTT p95: 0.239～0.667 ms
- RTTx p95: 59.75～133.4倍
- RTTx > 1.5のサンプル割合: 96.56～100%

絶対RTTは1 ms未満であり、強いネットワーク輻輳を示していない。それにもかかわらず
RTTxが非常に大きいのは、ループバック相当の環境で最小RTTが極端に小さく、
現在RTT / 最小RTTという比率が不安定になったためと考えられる。

現在のCUBIC判定はRTTx > 1.5だけで成立するため、RTTをONにした時点でほぼ常時
輻輳候補になる。RTTを含む8条件のうち7条件でGuardrailが157～217回作動した。

### 2. Guardrailと通常ABRが競合して品質が発振している

RTTを含みGuardrailが作動した条件では、品質切替が124～171回発生した。
平均ビットレートも約0.434～0.519 Mbpsで、上位品質を維持した条件の
約1.35～1.41 Mbpsより大幅に低い。

これはGuardrailが品質を1段階下げた後、Throughput/BOLAが再び上位品質を選び、
次のセグメント完了時にGuardrailがまた下げる動作を繰り返したためと考えられる。
1.5秒のcooldownだけでは、この上下動を十分に抑えられていない。

### 3. Loss条件は一度も成立していない

- 平均推定loss: 全条件0%
- p95推定loss: 全条件0%
- 再送増分ありのサンプル: 全条件0%

NoTC環境では再送が観測されなかったため、LossチェックのON/OFFは実際のABR判断に
影響していない。Loss単独条件とベースラインの差は、Loss制御の効果ではなく、
試行ごとのネットワーク・プレイヤ状態のばらつきと解釈すべきである。

### 4. CWND条件も一度も成立していない

- CWND最小値: 10～12 packets
- CWND圧迫条件成立率: 全条件0%
- CWND由来Guardrail: 0回

現在の条件は「CWNDが観測最大値の60%以下」かつ「未ACKパケットがCWNDの80%以上」
である。この同時条件は今回一度も満たされていない。したがって、CWND単独条件の
再生結果が良く見える場合も、CWNDをABRへ利用した効果ではなく、実質的には通常ABRである。

### 5. BOLA / RTT+LossだけGuardrailが0回なのは保護条件による

この条件でもRTTx > 1.5は100%成立している。しかし、バッファが8秒を超え、
stallCountが0の間はWatchingとして品質を下げないため、最後までGuardrailが
適用されなかったと考えられる。

反対に一度stallが発生すると、stallCount === 0という保護条件は以後成立しない。
その後バッファが回復してもGuardrailが作動し続けるため、最初のstallを境に
品質発振が継続する正のフィードバックになっている可能性が高い。

### 6. stall計測だけではQoEを捉えられていない条件がある

Throughput / Noneは記録stallが0秒だが、Playback excessは約80秒ある。
stallイベントとして記録されないセグメントスケジューラ停止または待ち時間が
含まれている可能性がある。そのため、今回の比較ではtotalStallMsだけでなく
総所要時間と再生位置の差も併用する必要がある。

## 現時点で言えること

1. TCPメトリクスAPIは、RTT/CWND/Lossをブラウザへ届け、選択状態に応じて
   Guardrailへ入力できている。
2. NoTC・CUBIC・ローカル低遅延環境では、RTTx比率1.5を固定閾値にする方法は
   輻輳検出として適切ではない。
3. 今回の品質変更は実質的にRTTだけが原因で、CWNDとLossの効果は評価できない。
4. 過剰なRTT検出により、通常ABRとGuardrailが競合して品質発振とQoE低下が生じた。
5. TCP情報を利用するAPIの成立と、その情報を使うABRアルゴリズムの有効性は
   分けて評価する必要がある。今回確認できたのは前者で、後者は改良が必要である。

## 改善案

### RTT判定

- 最小RTTが1 ms未満など極端に小さい場合はRTTxを無効化する
- RTT比率だけでなく、RTT - 最小RTTの絶対増加量も条件に加える
- 1サンプルではなく、連続3～5サンプルまたは移動中央値で判定する
- 接続開始直後の最小RTTをそのまま固定せず、時間窓付きbaselineを使う

### 品質制御

- Guardrail動作後、数セグメントは上位品質への復帰を禁止する
- downshift用閾値と復帰用閾値を分けてヒステリシスを持たせる
- 累積stallCountではなく、現在バッファ量と直近stallからの経過時間で保護する
- TCP信号だけで反復downshiftせず、バッファ減少やdelivery rate低下とのAND条件にする

### 実験設計

- 同一のtc/netemトレースを全条件へ適用する
- 各条件を最低5～10回繰り返し、平均・標準偏差・信頼区間を示す
- Loss評価では再送が実際に発生する条件を用意する
- CWND評価では帯域制限や輻輳を発生させ、CWND圧迫条件が成立することを確認する
- stallイベントに加えて、再生時間が進まない区間をheartbeatから直接集計する
